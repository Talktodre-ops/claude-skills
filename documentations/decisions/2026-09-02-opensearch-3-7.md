# OpenSearch 3.7 everywhere, upgraded ahead of the search platform deploy

**Date:** 2026-09-02
**Status:** Accepted
**PRs:** BE-heimly #111, #112; Infra-Heimly #5

**Context.** The search platform work (SP3 to SP7) moved the marketplace and
agent directory onto the index, which meant the engine version was about to
become load-bearing for the main product surface. AWS offered the prod domain
a single hop from 2.19 to any of 3.1, 3.3, 3.5 or 3.7. The client stack
(opensearch-py 3.2.0, django-opensearch-dsl 0.8.0) supports servers through
3.x, verified against the installed packages rather than search results,
which wrongly claimed a <3.0.0 cap from an older fork.

**Decision.** 3.7, in local, CI and prod, same version everywhere. The
reasoning that settled it: every breaking change lands at 3.0 (Lucene 10 and
the JVM 21 floor), so choosing an earlier 3.x buys no safety at all and only
shortens the runway to the next forced upgrade. Upstream was already on 3.8,
so 3.7 had a release cycle of soak.

Sequencing was the other half of the decision: upgrade the prod cluster
BEFORE deploying the search platform. At that moment the prod marketplace
still read from Postgres, so a failed blue/green would have cost autocomplete;
after the deploy the same failure takes down the marketplace. The window
closed the moment the backend shipped. The upgrade ran with the AWS
pre-upgrade check first (SUCCEEDED), took about 35 minutes blue/green on the
single node, and served traffic throughout.

Local verification bar before touching prod: all 13 indices rebuilt to counts
identical to 2.19, every endpoint matching baseline including the fuzzy typo
probes, and ordering parity against the ORM across all six sort options,
which covers the two most likely Lucene-major casualties, the Painless
ranking script and the explicit null-ordering sort parameter.

**Rejected.** 3.1/3.3/3.5 (no risk reduction, shorter runway). Deploying the
search platform first (turns an autocomplete-risk upgrade into a
marketplace-risk one). Migrating the data volume locally (indices are fully
derived from Postgres, so a clean volume plus reindex removes the Lucene 9 to
10 question).

**Revisit when.** AWS offers 4.x from 3.7, or the domain grows past a single
node, which changes the blue/green risk profile entirely.
